# World, VM, action, and menu firmware review (CreatureGathererFX-62u.3)

Review date: 2026-10-10. Read-only review, about 10 minutes wall time. No source edits, builds, tests, or fresh resource measurements were made. The supplied `build/06g-choice-shipping/CreatureGathererFX.ino.elf` reports 23,488 B flash (`.text` 23,432 + `.data` 56) and 1,747 B static SRAM (`.data` 56 + `.bss` 1,691). It predates later edits to some save sources, so its symbol sizes describe that checkpoint, not a promise about a rebuilt mutable tree. Named symbol ranges include inlined work and cannot be added to predict whole-image savings.

## Actual shipping reachability and contracts

- Default shipping calls `WorldEngine::runMap`, `drawMapFast`, `WorldEngine::interact`, `ScriptVm::initWarpVM/runWarpVM`, `onStep`, encounter selection, and plant growth. `CGFX_FULL_WORLD_VM` selects the full interpreter and popup path; trainer, wild, and arena demos are separate opt-ins. The current authored `scripts.hpp` has only three populated slots (0, 32, 33), each using `If`/`TpIf`/`End`; `text.bin` contains the empty two-byte count. The `Makefile` runs `tools/check-world-script-profile.cpp` before default build/Mini and rejects full-only opcodes and script text. These are profile-specific facts, not permission to drop future dialogue mechanics.
- The profile checker proves slot size, command boundaries, allowed opcodes, an `End`, and empty text. It does **not** prove flag index validity, condition type, jump target/boundary, or teleport coordinate range. The Rust builder in `../CreatureGathererTools/crates/core/src/builder.rs` compiles scripts, appends `End`, bounds each slot to 128 B, and assigns flag IDs; its `script/mod.rs` emits branch lengths as `u8` casts. Strengthen the packed-image checker before deleting runtime protection that depends on those properties. The 30-command cap is unreachable for a structurally valid 128 B compact stream (smallest command is 6 B), but keep it for the full VM and any expanded profile.
- `WorldTransient` is 191 B: 128-byte script/motion overlay, 43-byte property window, 20-byte encounter cache. `modeState` is 191 B in the ELF. A 4-byte movement snapshot in `WorldEngine::interact` is required because reading the script overwrites the motion overlay; removing it would break facing and in-progress movement after interaction. Map rows are streamed during render, and the property window is needed for collision before the next render and encounter gating at a committed destination. Do not replace those with per-step FX reads.
- `MenuV2`, `InventoryMenu`, item-name/definition helpers, `Action::setActionType`, `Event::loadEvent`, and the full-dialog renderer have no identifiable default shipping caller in the inspected source/ELF. The inventory menu draft is not yet opened by gameplay. Rewriting these in isolation does not recover application flash today; their future feature cost should be measured when connected. Existing `CreatureGathererFX-2ua` already owns the measured `ScriptVm::memory[8]`/`stack[8]` trim (-16 B SRAM, 0 B flash in an older control); do not count it again.

## Ranked independent experiments

1. **Stream the compact warp interpreter from the borrowed slot, after completing host checks.** `src/vm/ScriptVM.cpp` currently scans all command boundaries in `initWarpVM`, then `runWarpVM` redecodes with per-operand `readUInt8/readUInt16` pointer/length checks, null checks, a 30-command loop, flag-index checks, and jump bounds. For the default authored profile, make `tools/check-world-script-profile.cpp` verify flag indices against generated flag capacity, `If` condition/branch encoding, jump targets and command boundaries, and `TpIf` coordinates within the 256×256 map. Then try one bounded offset-based pass over `world.script`, retaining exact big-endian operand and live-location semantics; keep the existing full VM available for `CGFX_FULL_WORLD_VM`. The compact path has no popup or pause, so it need not retain a global continuation cursor once the host contract is complete. `vm` occupies 27 B `.bss` in the checkpoint; the 16-byte array reduction is already planned by 2ua, so incremental static benefit after that bead is at most the remaining 11 B. Flash benefit is **unmeasured**; report whole-image delta separately from host-checker size. Verify three packed warps, both flag values, skipped branch, high coordinate 255, invalid/empty content rejected at build, and `test_scripts` plus `test_stack` device behavior. Do not remove full-VM malformed-script handling or assume arbitrary hand-built bytecode is authored content.

2. **Omit the default-profile dialog queue and its battle clearing calls.** The checkpoint ELF retains `dialogMenu` as 85 B `.bss` and `DialogMenu::clear()` as a named 44-byte text range. `CreatureGathererFX.ino` declares the queue; `BattleFlow::update/finishBattle` peeks/clears it, but the compact world path returns `false` for dialog activity, the compact VM cannot emit messages, and the default renderer omits popup drawing. A profile-specific compile boundary around this global and the two battle calls should retain the full queue in full-VM builds and explicit dialog device tests. The **maximum direct static saving is 85 B** in the checkpoint; actual flash and static deltas require a build because LTO and shared code can change them. Check battle completion and immediate return to world, no stale popup after trainer/arena callback, full-profile message queue/dismissal, and device `test_stack`. A future script with messages must trigger the existing build guard or select full VM; silently ignoring it is unacceptable.

3. **Store only gameplay-consumed tile bits in the world cache.** `TilePropertyWindow.hpp::writeRow/lookup` packs seven bits per cell (six tile properties plus GID presence), using 40 data bytes and three origin/row-valid bytes. Default gameplay reads only walkable (`WorldCollision::canEnter`) and encounter (`StepEvent::rollEncounterOnStep`) plus GID presence. A three-bit cell (walkable, encounter, occupied) takes 17 data bytes for 45 cells, or 20 B total, reducing `WorldTransient` by 23 B. Actual `ModeState` SRAM saving can be anywhere from 0 to 23 B because the battle member may become the union maximum; flash is **unmeasured** and bit packing may change it either way. Preserve signed viewport origins, valid-row invalidation on teleport/step, GID-zero blocked behavior, the sealed encounter fixture at (255,255), and exact row FX-read counts. This deliberately narrows the cache API: full six-bit property preservation is tested by `tst/tile_props_test.hpp` but no shipping caller consumes water/plantable/lure/spare today. Adapt tests to actual collision/encounter outcomes and add a compile/build assertion when a later world mechanic starts consuming another property. Prefer this only if the measured whole-image or reserve gain justifies the narrower profile.

4. **Validate authored encounter tables on the host, then test a narrower transition loader.** `src/engine/world/Encounter.cpp::load` scans all eight ten-byte zone definitions on each chunk transition; `fxdata/data/encounters.txt` currently has one real zone and seven `0xffff` sentinels. The same load checks table count/range, species IDs, and floor/ceiling; `select` repeats those checks on the RAM cache on each encounter step. This hand-authored `encounters.txt` is packed directly by `fxlayout.toml`: unlike map scripts, no discovered host semantic validator proves those fields today, so these guards cannot simply be deleted. Add a native authoring/packed-image check for active zone IDs and table spans, all ten species IDs, inclusive level floor/ceiling, and sentinel layout. Then independently measure either a generated active-zone count (one now, with future additions enforced) or removal of duplicated table-validity scans from `select`. Keep cache-valid/no-zone, empty party, species-zero, RNG ownership, and level clamping as real runtime states. The authored map has one encounter-property tile at sealed border (255,255), while the opt-in wild demo forces a first-step roll; neither route may regress. Potential flash and transition-read savings are **unmeasured**; do not claim eight records' byte count as firmware savings.

5. **Try byte-wise plant-stage progression.** `PlantGameState::tick` calls `PlantStage::incrementAll` every 128 committed steps; the latter loops 32 times through per-index two-bit extraction and replacement. Each of the eight packed bytes could advance four independent modulo-four stages with `old ^ 0x55 ^ ((old & 0x55) << 1)`, then store the byte. This retains the exact 0→1→2→3→0 cycle, eight-byte save format, ticker timing, and no growth on partial movement. It avoids 32 index calculations and calls, but the whole plant step hook released only 86 B in an older broad removal diagnostic, so code saving is bounded and **unmeasured**. Verify all four starting stages in all 32 positions, tick 127/128, battle interruption, save round-trip, and a focused stack run if the helper changes call depth.

`WorldEngine::runMap` also calls `moveable` when accepting input and again before the first `moveChar` on the same frame; movement then checks the same cached destination on subsequent frames. A later small experiment could skip repeat lookups only after a successful checked start. Its likely value is frame time, not established flash savings; preserve first-pixel timing, collision edges, teleport cancellation, and chunk/step dispatch. It is lower priority than the five independent measurements above.

Suggested per-experiment evidence: same-flag `make ram` control/candidate ELFs, `make test`, `make testvm`, `make test-world-script-profile world-script-profile-check`, focused `make fxtest-spike FXTEST_SPIKE_INO=tst/fxdatatest/test_scripts.ino ARDENS=/path/to/Ardens`, then the required `make final-gate` only after implementation and edge-case review. Run `make test-pack-parity` if generated/packed bytes change. Compare actual shipping flash/static and painted stack reserve, not named symbol totals; separate each experiment so LTO effects remain attributable.
